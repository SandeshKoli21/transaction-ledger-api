# Transaction Ledger API

A backend API for a simple transaction ledger: create accounts, post credits and debits, read balances and paginated history, and transfer money between accounts atomically (bonus).

- **Runtime:** Node.js 22.5+ (built-in `node:http` and `node:sqlite`)
- **Database:** SQLite (relational, file-based)
- **Dependencies:** none, so there is no `npm install` step

## Run locally

```bash
node --version        # must be 22.5 or newer
npm start             # API on http://localhost:3000
npm test              # runs 13 end-to-end tests against an in-memory database
```

Optional environment variables: `PORT` (default `3000`), `DB_FILE` (default `ledger.db`).

## Quick try (curl)

```bash
# 1. Create an account
curl -s -X POST localhost:3000/accounts -H "Content-Type: application/json" -d '{"name":"Asha"}'

# 2. Credit 100 (replace ACC_ID)
curl -s -X POST localhost:3000/accounts/ACC_ID/transactions -H "Content-Type: application/json" \
  -d '{"type":"credit","amount":100,"reference_id":"ref-1","description":"Salary"}'

# 3. Balance and history
curl -s localhost:3000/accounts/ACC_ID/balance
curl -s "localhost:3000/accounts/ACC_ID/transactions?type=credit&page=1&limit=10"
```

Full endpoint reference: [API.md](API.md)

## Project structure

```
src/
  server.js     entry point: wires DB -> ledger -> HTTP app
  app.js        HTTP routing, JSON parsing, consistent error responses
  validate.js   all request validation (body + query params)
  ledger.js     business rules: balances, duplicates, atomic writes, transfers
  db.js         schema, constraints, immutability triggers
  errors.js     AppError (status + code + message)
test/
  api.test.js   end-to-end tests for every rule in the brief
```

Each layer has one job: HTTP knows nothing about SQL, and the ledger knows nothing about HTTP.

## How the key rules are guaranteed

| Rule | How |
|---|---|
| Initial balance is 0 and the client can't set it | The `INSERT` always writes `0`; a request containing `balance` is rejected with 400 |
| Transaction + balance update are atomic | Both writes run inside one `BEGIN IMMEDIATE ... COMMIT`; any error triggers `ROLLBACK` |
| No overdraft | Checked in code before writing, and backed by the DB constraint `CHECK (balance >= 0)` |
| Duplicate `reference_id` per account | Checked in code (returns 409 with the existing transaction), backed by `UNIQUE(account_id, reference_id)` |
| Same `reference_id` across accounts is allowed | The uniqueness is per account, not global |
| Transactions are immutable | No PUT/PATCH/DELETE routes (405), and DB triggers abort any `UPDATE`/`DELETE` on `transactions` |
| Latest-first ordering | `ORDER BY created_at DESC, seq DESC` (`seq` breaks ties within the same millisecond) |
| Transfer is all-or-nothing | The debit and credit run in a single DB transaction; if either leg fails, both roll back |
| Exact money arithmetic | Amounts are stored as integer paise, so `0.1 + 0.2` is exactly `0.3` |

## Assumptions

1. **Currency and precision:** single currency; amounts accept at most 2 decimal places and are stored internally as integer minor units (paise).
2. **IDs** are UUIDs generated by the server for both accounts and transactions.
3. **Duplicate response:** a repeated `reference_id` returns `409 DUPLICATE_TRANSACTION` with the original transaction in `details`, so a client retry can tell what already happened.
4. **Insufficient balance** returns `422` (valid request, but it breaks a business rule). Validation problems return `400`.
5. **`description`** is optional (max 500 chars). **`name`** is required (max 200 chars).
6. **Pagination defaults:** `page=1`, `limit=10`; `limit` is capped at 100.
7. **Transfers** require a `reference_id`. It is recorded as a debit on the source and a credit on the destination with the same `reference_id`, so a retried transfer is rejected as a duplicate. Transferring to the same account is not allowed.
8. **Concurrency:** SQLite `BEGIN IMMEDIATE` takes a write lock, so concurrent writes to the same account are serialized and balances can't race.
9. **Authentication** is out of scope for this assignment.
